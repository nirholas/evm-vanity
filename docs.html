Quick start

Grind in the browser at the grinder: nothing to install, and the key never leaves the tab.

git clone https://github.com/nirholas/evm-vanity
cd evm-vanity
npm install
npm run dev          # site on :5181, API on :8788

Or from the command line, with nothing cloned:

npx evm-vanity grind --prefix beef --keystore wallet.json
npx evm-vanity quote --prefix dEaD
npx evm-vanity delegate --prefix beef
npx evm-vanity inspect 0xdEaD…

The difficulty model

An EVM address is the low 20 bytes of a Keccak-256 digest, rendered as a fixed 40-character hex string. There is no length variance and no leading-zero stripping, so every nibble is independently uniform at both ends. The honest model really is 16⁻ⁿ, and 0x0000… costs exactly what 0xdead… costs.

That is true of all three derivations this project deals with:

EOA      address = keccak256(uncompressed pubkey[1:])[12:]
CREATE   address = keccak256(rlp([sender, nonce]))[12:]
CREATE2  address = keccak256(0xff | deployer | salt | initCodeHash)[12:]

The number people do get wrong is casing. EIP-55 re-cases the hex letters using bits of keccak256(lowercase address), which behave as fair coin flips, so asking for a specific spelling costs an extra factor of two per letter: dEaD is sixteen times harder than any-case dead. Digits carry no case and cost nothing. Every quote here reports that multiplier explicitly.

Grinding is geometric, so the expected value is not a deadline: at the expected attempt count you have had a 63.2% chance of finishing, and one run in twenty takes three times as long. Quotes report p50, p90 and p99 next to the mean because a decision to pay for a grind depends on the tail, not the average.

Entropy, and the Profanity break

In 2022 the most popular EVM vanity generator, Profanity, was found to seed its search from a 32-bit value. Every key it had ever produced was therefore searchable, and tens of millions of dollars were drained from addresses it had generated. The lesson is not "vanity addresses are unsafe": it is that the seed is the whole security of the scheme.

This grinder draws a full 256-bit base scalar from the platform CSPRNG, and:

  • walks incrementally from it (k+i, one point addition per candidate) which is as secret as the base scalar,
  • re-seeds every million candidates so no single run extends one arithmetic progression indefinitely,
  • re-derives every match from scratch through a separate code path and refuses to emit a key that does not control the address it matched.

All three checks live in src/eoa-grinder-worker.js and src/grinder-node.js, and the last one has a test.

Split-key delegation

Hard patterns need more compute than a browser tab has, and handing the job to someone else normally means handing over the key. Split-key grinding removes the trade with group arithmetic on secp256k1, generator G, order n:

  1. The requester picks a secret scalar k1 locally and publishes only P1 = k1·G.
  2. A worker searches offsets k2, testing the address of P1 + k2·G against the pattern. It knows k2 and P1 but not k1, so it cannot compute the private key.
  3. On a hit it returns (k2, A). Anyone can check that the address of P1 + k2·G equals A, with no secret in the calculation.
  4. The requester combines k = (k1 + k2) mod n on their own machine.

The offset is not a secret: it is useless without k1, so it travels in the clear with no envelope, no escrow and no trusted delivery.

And on secp256k1 there is no catch. Private keys on this curve are scalars, so the combined result is an ordinary 32-byte key that imports into MetaMask, ethers, viem, Rabby or a keystore file like any other. The Ed25519 version of this trick, used on Solana, produces an expanded key that seed-only wallets reject. Here, delegated grinding costs you nothing at all.

Try it on the delegation page, or from the CLI with evm-vanity delegate.

EIP-712 attestations

An attestation is a signed statement about how an address was produced: the pattern, the difficulty under a named model, the grind format, a freshness nonce, and for a split-key grind the two public points whose sum is the address.

It is signed as EIP-712 typed data rather than as an opaque blob, because the interesting verifier on EVM is on chain: a marketplace, a registry or an escrow recovers the signer with ecrecover in three lines of Solidity and can refuse to list an address that is not provably ground and never custodied. The verify page carries the Solidity, and the exact type hash and domain separator are served at /.well-known/evm-vanity.json so a contract and this library cannot drift apart.

The domain deliberately carries no chainId and no verifyingContract: an attestation is a statement about an address, and an address is the same on every EVM chain. Pinning one would make a true statement fail to verify after a bridge.

Verification recomputes every claim rather than trusting the document, and reports each one:

import { verifyAttestation } from 'evm-vanity/attestation';

const issuers = (await (await fetch(BASE + '/.well-known/evm-vanity.json')).json()).issuers.map(i => i.address);
const result  = verifyAttestation(attestation, { issuers });

result.valid;    // true / false
result.checks;   // per-check audit with human-readable detail

Without an issuer list a self-signed forgery passes the signature check, because it signed itself. The verifier says so rather than passing quietly.

Chains

One grind covers every EVM chain: the address is derived from the key, not from a network. The registry in src/chains.js exists for the explorer links and for the deterministic CREATE2 deployers, which matter only if you later want a contract at a vanity address.

Every row was verified with eth_getCode against the listed public RPC, and the chains page re-runs that check from your browser so the table can be re-verified rather than trusted. Ethereum, Base, Arbitrum, Robinhood Chain, OP, Polygon, BNB and Avalanche carry all four deployers; Robinhood Chain's testnet is missing only the Coinbase Smart Wallet factory.

HTTP API

Machine-readable schema: /openapi.json. Agent card: /.well-known/agents.json.

EndpointWhat it does
POST /api/quoteProbability, expected attempts, p50/p90/p99, rarity, and the EIP-55 case multiplier.
POST /api/inspectValidate an address, check its checksum, and score the pattern it carries.
GET /api/chainsThe chain and deployer registry.
POST /api/attestSign an EIP-712 attestation. Refuses an address that does not match the claimed pattern.
POST /api/verifyVerify one against the published issuer list.
POST /api/splitkey/grindDelegated grinding. Send p1 and a pattern, get an offset back.
POST /api/splitkey/verifyCheck that an offset really produces a claimed address.
POST /api/grindCustodial server-side grind. Disabled unless the operator sets ALLOW_SERVER_GRIND=1.

CLI

npx evm-vanity grind --prefix beef --suffix dead --keystore wallet.json
npx evm-vanity grind --prefix BeeF                 # EIP-55 spelling, 16x harder
npx evm-vanity delegate --prefix beef --api https://evm-vanity.dev
npx evm-vanity quote --prefix beef --rate 17000
npx evm-vanity inspect 0xdEaD…
npx evm-vanity verify attestation.json
npx evm-vanity chains --verify                     # re-probe every RPC

grind runs one worker per core. delegate runs the split-key protocol against a remote API and combines locally, so it is safe to point at a service you do not control. Add --json to anything for machine-readable output.

Self-hosting

One Fetch handler, two hosts, no endpoint that behaves differently between them.

npm run build
ATTESTATION_KEY=$(node server/keygen.mjs | head -1 | cut -d= -f2) npm start
npm run build
npx wrangler secret put ATTESTATION_KEY
npx wrangler deploy
VariableMeaning
ATTESTATION_KEY32-byte secp256k1 key (hex) for signing attestations. Unset means an ephemeral per-process key, which the API reports in every response.
ALLOW_SERVER_GRINDSet to 1 to enable the custodial grind endpoint. Off by default, on purpose.
PORTNode listen port. Default 8788.

The attestation key is a signing identity, not a wallet. Do not fund it: it never needs gas, and the service never sends a transaction.
